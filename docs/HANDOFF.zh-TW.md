# 交接文件

這份文件說明專案現在做到哪裡、哪些驗證過、哪些沒有、接手後該先做什麼。設計與規則本身寫在 [TECHNICAL_HANDBOOK](TECHNICAL_HANDBOOK.zh-TW.md)，這裡不重複。

## 一句話現況

核心邏輯、桌面外殼、介面三塊各自完成並通過自動測試，外殼已在 Windows 11 實機執行；**三塊之間還沒接起來**，桌面程式顯示的是假資料，也從未連過真實模型。

### 桌面外殼 `src-tauri`（crate `elf-shell`）

24 項測試通過。已在使用者的 Windows 11 上以 `npm run tauri dev` 建置並執行。

- 三個視窗：浮動精靈、主面板、設定（需要時建立，關閉即銷毀）。
- 系統匣選單：開啟、暫停觀察、勿擾、結束。兩個開關目前只記住勾選狀態，沒有實際作用。
- 關閉主面板是隱藏；只有系統匣的「結束」會退出。
- 單一執行個體。
- 浮動視窗：透明、可拖曳、輪盤展開時以精靈為中心放大、位置保存與還原。
- 命令只有三個：`app_info`、`open_window`、`set_floating_expanded`。
- **`elf-core` 列為相依套件但沒有被呼叫。**

### 前端 `src`

約 7,400 行。型別檢查與建置通過，Playwright 介面檢查 157 項通過（在瀏覽器中，以假後端）。

- 對話、任務中心、今日面板、授權確認卡、設定（模型、觀察與隱私、記憶、外觀）。
- 浮動精靈：六種狀態、輪盤、貼邊收合。
- 六款可切換造型，各有平面與 2.5D 分層兩套素材；兩個配色系列，淺色與深色主題。
- 所有資料來自 `src/lib/ipc-mock.ts`。在 Tauri 內只有 `open_window`、`set_floating_expanded` 走真實命令。
- 外觀設定目前存在瀏覽器的 localStorage，不是資料庫。

## 驗證範圍

### 在 Windows 實機確認過（使用者回報）

- 專案可以編譯並啟動，包含核心與內建 SQLite。
- 主面板顯示正常，中文與深色主題無誤。
- 浮動精靈出現在桌面，背景透明，可以拖曳。
- 設定視窗可開啟，四個分頁都在。

### 只在 Linux 或瀏覽器驗證過，Windows 上未確認

- 輪盤展開與收合時精靈是否跳動；靠近螢幕邊緣時的位置。
- 2.5D 版的顯示、動態、半透明圖層的透明效果（已同步給使用者，尚未回報）。
- 位置保存與還原、舊位置的換算、多螢幕與不同縮放比例。
- 系統匣圖示與選單、單一執行個體、選「結束」後是否完全退出。使用者尚未明確回報這幾項。
- 視窗隱藏時動畫是否暫停。
- 核心中 `#[cfg(windows)]` 的**測試**從未執行過（非測試程式碼已隨桌面程式在 Windows 編譯成功）。Windows 路徑規則（UNC、裝置路徑、替代資料流、大小寫、`\\?\` 前綴、junction）都只用字串在 Linux 上測過。

### 完全沒有驗證

- 安裝包。

## 接手後的工作順序

1. **在 Windows 上跑一次核心測試。** `cargo test -p elf-core`。這會第一次執行 Windows 專屬的路徑測試，預期可能有需要修正的地方。建議同時設定 CI 在 Windows 上跑。
2. **把核心接上外殼（最重要）。** 讓 `submit_task`、`cancel_task`、`get_task`、`list_tasks`、`respond_to_approval`、對話、模型設定等命令呼叫 `elf-core`：
   - 資料庫放在應用程式資料目錄；啟動時跑 migration 與 `recover_after_restart`。
   - 憑證存 Windows 認證管理員，實作 `CredentialStore`；前端只能寫入，不能讀回。
   - 把協調器的 `EventSink` 事件轉成 Tauri 事件送給前端。
   - 定時呼叫 `expire_stale_approvals`。
   - 由 Rust 型別產生 TypeScript 定義，取代手寫的 `src/lib/ipc-types.ts`。目前前端型別與核心型別是各自寫的，欄位已有出入（核心事件新增了 `unresolved`、核准的 `resolved_resource`、`expires_at` 等）。
   - 前端以 `VITE_IPC=tauri` 切到真實後端；建議逐個命令遷移，沿用 `withNativeCommands` 的做法。
   - 外觀設定改存資料庫的 `settings` 表。
3. **用真實 API key 驗證兩個適配器。** 先對話，再工具呼叫，再中途取消與限流。預期要修正線路格式的細節。尚不知道使用者有哪幾家帳號。
4. **排程器與通知。** 在外殼啟動排程器迴圈，實作 `Notifier`（系統通知）。通知在開發模式下顯示來源不正確，驗收必須用安裝版，所以要先產出 NSIS 安裝包。
5. **跑通第一個完整展示情境**（手冊第 13 章）：貼筆記 → 摘要與待辦 → 設定提醒 → 關閉主視窗仍收到通知 → 產生文件 → 任務卡顯示成果。
6. **第二輪安全審查。** 第一輪沒有涵蓋模型適配器、HTTP 傳輸與 Tauri 外殼；核心接上外殼後，IPC 命令的授權檢查是新的攻擊面。
7. P1 功能：網路研究、專案讀取與分析、活動採樣、主動建議、記憶。

## 已知問題與風險

### 安全（接上真實模型與外部工具前必須處理）

- 讀入外部內容後，模型仍可能透過「讀取外部網址」把資料帶出去。目前沒有網路讀取工具，所以尚不構成問題；做網路研究功能之前必須先設計對策。
- 對應到網路磁碟機的磁碟代號無法用字串判斷，只會在已授權的根目錄下被存取到。
- 串流中的工具參數片段在組裝完成前沒有大小上限（組裝後有 2 MiB 上限）。
- `tauri.conf.json` 的 CSP 目前是 `null`（開發伺服器需要）。發行前要設定限制性的 CSP。
- 目前沒有任何程式碼建立「使用者常設」授權。之後由設定頁建立時，範圍必須由 Rust 決定，不可接受前端傳入的值。
- migration 0004 之前建立的核准與訊息紀錄保留了完整參數，未回溯遮蔽。開發期的資料庫建議直接重建。

### 產品行為

- 純讀取的任務會以 `no_evidence` 失敗。規則是：分析與研究任務必須把結論寫成成果檔才算完成；只需回答的問題走對話路徑。做研究與開發類工具時要照此設計提示與流程。
- 排程器在「通知已送出、紀錄尚未更新」之間當機時，重啟後會重送一次提醒。這是刻意的取捨（寧可重複，不可遺漏）。
- 2.5D 造型在非待命狀態會隱藏光暈層，以守住 8 層上限。
- 拖曳時的傾斜只出現在開始拖的瞬間，因為 Windows 接手拖曳後網頁收不到滑鼠事件。要全程傾斜需由外殼轉發移動事件。
- 輪盤曾有一次在切換勿擾後無法再開啟，之後未能重現，原因不明；已加上保護但未確認根因。
- 輪盤目前是六張圍繞精靈的小卡，不是環狀扇形。使用者尚未表示是否要改。
- 貼邊收合圖沒有狀態版本，前端暫時在旁邊加狀態標記。

### 美術

- 純黑桌布上，星軌信使的深棕色環、葉披風與稜鏡書靈的深色輪廓對比偏低。
- 稜鏡書靈與紙燈的圖在畫布中偏離中心約 1 到 2 像素。
- 需要設計方補：每種狀態的收合圖。

### 工程

- `tests-ui/capture.cjs` 需要 Playwright，但它不在 `package.json` 的相依套件裡（開發環境預先安裝了）。接手後若要跑介面檢查，需自行安裝。
- 尚未設定 CI。
- 測試樣本有兩份（`docs/research/fixtures` 與 `crates/elf-core/fixtures`），修改時要同步。
- `.gitattributes` 把 `.sse` 與 `.http` 標為二進位，避免在 Windows 上被轉換換行而使樣本測試失敗；請勿移除。

## 這個專案是怎麼做出來的

由一個技術負責人指揮多個 AI Agent 平行開發：資料蒐集、程式開發、視覺設計各由不同 Agent 負責，每項交付都由技術負責人重跑測試後才合併，涉及授權的程式碼另由沒看過開發過程的 Agent 做獨立審查。流程與規則見手冊第 17 章，工作包與進度見 [WEEK_PLAN](WEEK_PLAN.zh-TW.md)。

提交歷史中每一筆的訊息都標明工作包編號（C1、F1、T1 等）與驗證方式，可對照 WEEK_PLAN 查閱。
